# PART 1: The Error Isolation Department (Custom Exceptions)

When building an enterprise system, we never want the application to crash with a generic Python error screen. Instead, we build a dedicated **Exception Hierarchy Layer**. This acts like a network of warning sirens, allowing our software to gracefully isolate errors and instantly communicate what went wrong to frontend apps and cloud monitoring platforms.

---

### Class 1: `ShopInsightError`

#### ──► Nutshell / TL;DR

The master blueprint for all specific errors across the entire app, allowing us to attach clear diagnostic web status codes to any failure.

#### ──► Company-Level Project Analogy

Think of this as a company's **Official Corporate Incident Report Template**. Every department uses this exact same form whenever something goes wrong, ensuring that whether a failure happens in billing, shipping, or security, every report contains a standardized "Incident Code" and "Description" so managers can read them instantly.

#### ──► Why It's There (Junior Context)

Standard Python exceptions like `ValueError` only let you store a text message string. However, in modern corporate web applications, the backend code needs to communicate with mobile apps and browsers. Web servers communicate using numeric **HTTP Status Codes** (like 401 for unauthorized, 404 for missing). By building a base custom exception that bundles a text `message` with a numeric `code`, we make it incredibly easy for our API gateways to instantly convert a code crash into an accurate web response without writing messy conversion logic.

#### ──► How It Works

* `class ShopInsightError(Exception):` tells Python that this class inherits all powers from the built-in native `Exception` class, allowing it to halt execution and generate debug trackings (tracebacks).
* **Method: `__init__(self, message, code=400)**`
* `super().__init__(message)` passes the text string directly up to the native Python exception handler so logs track the basic error string.
* `self.message = message` and `self.code = code` capture these parameters and lock them directly onto the error instance for our web framework to read later.


* **Method: `__str__(self)**`
* This is a special Python hook method. Whenever a developer prints the error or logs it to the cloud console (`print(error)`), Python automatically routes to this method. It formats the output into a clean string layout: `"[400] Bad Request Text"`.

* When called, it immediately executes `super().__init__(message, code=401)`. This intercepts the construction phase and forces the HTTP response code to **401**—the universally recognized internet standard status code for authentication and credential clearance failures.

# PART 3: The Memory Collections Engine (Identity Hashing & Sorting Protocols)

This layer deals with **Data Comparison and Memory Structuring Magic Methods**. In an enterprise Python application, you constantly place objects inside lists, sets, and dictionary keys. ### Method 1: `User.__eq__(self, other)`

#### ──► Nutshell / TL;DR

Teaches Python how to check if two distinct user variables actually represent the same person by inspecting their core database identity tokens instead of their random RAM addresses.

#### ──► Company-Level Project Analogy

Imagine two separate paper printouts of the same customer profile sitting on two different desks in the office. Physically, they are two separate pieces of paper (separate memory allocations), but the account manager looks at the **Customer ID** and **Email** printed on both pages and says: *"These are the exact same customer account. I can shred one."*

#### ──► Why It's There (Junior Context)

By default, if you type `user1 == user2`, Python checks if they share the exact same memory pointer location (`id(user1) == id(user2)`). In a real web app, if you fetch a user profile from the database during page load, and then fetch the same user profile again inside a shopping cart microservice, they will sit at two different memory spots. Without `__eq__`, your code would claim they are different users, breaking comparison checks, testing tools, and data updates.

#### ──► How It Works

* This method intercepts the native Python `==` comparison operator.
* It first runs a safety type check: `if not isinstance(other, User): return NotImplemented`. This tells Python: *"If you are trying to compare a `User` object to a plain string or an integer, I don't know how to do that, so skip this logic."*
* If the other object is a `User`, it executes the absolute matching logic rule: `return self.user_id == other.user_id and self.email == other.email`. It returns `True` only if both properties match identically.

---

### Method 2: `User.__hash__(self)`

#### ──► Nutshell / TL;DR

Generates a unique numerical fingerprint (hash value) for a user instance, allowing it to be indexed and fetched instantly inside high-speed data structures like Python `Set` groups and `Dictionary` keys.

#### ──► Company-Level Project Analogy

Think of a bank's massive **Safety Deposit Box Locker Vault**. Instead of a clerk spending hours walking room to room searching through every locker for your file, they take your Customer ID and Email, pass them through a fast code generator machine, and it instantly prints out a precise locker location code: `Box #9042`. They go straight there in a fraction of a second.

#### ──► Why It's There (Junior Context)

If you want to filter out duplicates from an array of 10,000 users, the most efficient way in Python is to convert the list into a set: `unique_users = set(user_list)`. Sets provide $O(1)$ constant-time lookups because they use hash values to organize elements. However, Python strictly mandates a rule: **If you customize how `__eq__` works, you must also provide a custom `__hash__` method.** If you don't, Python will mark your class as unhashable and throw a fatal crash (`TypeError: unhashable type: 'User'`) when you attempt to use sets or dictionary keys.

#### ──► How It Works

* When Python tries to insert or look up this object inside a set or dictionary key map, it triggers `__hash__(self)`.
* It bundles the defining identifying characteristics of the account user into a single immutable data structure called a tuple: `(self.user_id, self.email)`.
* It passes this tuple into Python's native internal hashing algorithm: `return hash((self.user_id, self.email))`. This generates a secure, fixed-size mathematical integer signature that reliably identifies that specific object state.

---

### Method 3: `User.__lt__(self, other)`

#### ──► Nutshell / TL;DR

Implements the "Less-Than" (`<`) operator for user instances, allowing arrays of users to be cleanly organized in ascending numerical order by their database IDs automatically.

#### ──► Company-Level Project Analogy

An HR manager receives a messy, unsorted stack of 50 new employee folder profiles. To clean up the desk, the manager flips through the files and physically stacks them in order from the oldest employee number to the newest employee number by reading the numeric ID badge value stamped on the cover tab.

#### ──► Why It's There (Junior Context)

Python natively understands how to sort standard numbers (`1 < 5`) and strings (`"A" < "B"`), but it has no idea how to sort complex objects. If you have an unsorted array of users and run `user_list.sort()`, Python will crash because it doesn't know if a "Shopper" role is smaller than an "Admin" role, or if a user named "John" is smaller than "Jane". Overriding `__lt__` sets a clear corporate sorting policy, making array sorting seamless.

#### ──► How It Works

* This method is called automatically whenever your code uses the `<` symbol between two user instances, or when calling automated sorting utilities like `sorted(user_list)` or `user_list.sort()`.
* It validates the incoming type using `isinstance(other, User)`.
* It evaluates the comparison expression: `return self.user_id < other.user_id`. It sends back `True` if the current instance's system index number is lower than the target comparator object's index number.

---

### Method 4: `User.__le__(self, other)`

#### ──► Nutshell / TL;DR

Implements the "Less-Than-or-Equal-To" (`<=`) comparison operator for user instances, completing the sorting logic coverage.

#### ──► Company-Level Project Analogy

A corporate security access checkpoint line. The supervisor instructs a security guard: *"You are only allowed to process records for batch processing if their registration ticket sequence number belongs up to or is exactly equal to Batch Number 500."*

#### ──► Why It's There (Junior Context)

While implementing `__lt__` (`<`) handles the vast majority of sorting requirements, enterprise systems often rely on advanced boundary algorithms—such as binary search routines, range filters, or paginated database offset windows. Providing the complete logical set of operators prevents edge-case comparison errors when two records have identical boundary properties.

#### ──► How It Works

* This method intercepts the `<=` comparison operator.
* It directly checks the instance value state against the comparator target value state: `return self.user_id <= other.user_id`, returning a clean boolean flag to the calling script thread.

### Decorator Property: `@property def full_name(self)`

#### ──► Nutshell / TL;DR

Dynamically generates a user's combined first and last name on demand so you don't waste memory storing a redundant third variable.

#### ──► Company-Level Project Analogy

An automated corporate badge reader. When you scan your card, the scanner looks up your separate "First Name" and "Last Name" database fields and dynamically displays them combined as a single line on the monitor screen.

#### ──► Why It's There (Junior Context)

**Avoid stale data vulnerabilities at all costs.** If you calculate a full name once inside `__init__` and store it as a normal variable (`self.full_name = first_name + last_name`), what happens when a user updates their last name after getting married? Your stored `full_name` becomes outdated and out of sync. Using the `@property` decorator tells Python to calculate this value dynamically *only when someone explicitly asks for it*, guaranteeing the data is always up to date.

#### ──► How It Works

* The `@property` decorator turns a standard method into a **read-only virtual attribute**.
* Other parts of your program access it without using parentheses: `print(user.full_name)` instead of `user.full_name()`.
* When called, Python executes the string format evaluation: `return f"{self.first_name} {self.last_name}"` and drops the resulting text string back to the calling line.

### Security Flags: `is_admin`, `is_analyst`, & `is_premium`

#### ──► Nutshell / TL;DR

Quick boolean (`True`/`False`) switches that let developers check an account's primary role classification instantly without typing messy string equations.

#### ──► Company-Level Project Analogy

Brightly colored clearance stickers stuck to the front of a corporate security badge. A guard looks at a badge, spots a yellow sticker, and instantly knows: *"This person is an analyst,"* without needing to read the fine print on the back of the card.

#### ──► Why It's There (Junior Context)

Writing hardcoded string checks like `if user.role == "admin":` throughout a massive project with hundreds of files is highly error-prone. If a junior developer makes a typo and writes `if user.role == "Admin":` (with a capital A), the security check fails silently, causing hard-to-track bugs. Centralizing these lookups into properties like `user.is_admin` provides autocomplete in your IDE and eliminates raw string comparisons from your application logic.

#### ──► How It Works

* `is_admin` evaluates `return self.role == "admin"` and hands back a boolean.
* `is_analyst` evaluates `return self.role == "analyst"`.
* `is_premium` checks for broader tier containment: `return self.role in ["admin", "analyst"]`. This allows both roles to unlock advanced features through a single clean condition check.

### Static Method: `@staticmethod def _is_valid_email(email: str)`

#### ──► Nutshell / TL;DR

An isolated helper tool that validates the basic characters of an email address string without needing an active user object to run.

#### ──► Company-Level Project Analogy

An automated passport scanning machine at an airport gate. It doesn't care who you are, how much money you have, or what your destination is; its only job is to scan the text structure of your passport code to ensure it matches global layout regulations.

#### ──► Why It's There (Junior Context)

This is a **pure utility function**. It represents the concept of *Separation of Concerns*. Checking whether a text string looks like an email address doesn't require knowing a user's password or first name. By decorating it with `@staticmethod`, we tell Python to decouple it from individual object instances. This saves memory and allows other modules to use this validation check without spinning up a fake user object.

#### ──► How It Works

* The `@staticmethod` decorator tells Python not to pass the automatic instance parameter `self` into the method arguments.
* The leading underscore (`_is_valid_email`) is a Python convention warning other developers that this is a **private utility method** meant to be called only inside this class box.
* It uses string methods: `return "@" in email and "." in email.split("@")[-1]`. It verifies that an `@` symbol exists and that a dot (`.`) exists somewhere in the domain string *after* that `@` symbol.

### Instance Guard Method: `def validate(self)`

#### ──► Nutshell / TL;DR

The pre-flight checklist that self-audits the current object instance to ensure all data fields are structurally valid before anything gets saved to a file or database.

#### ──► Company-Level Project Analogy

A quality assurance engineer checking an assembled product at the end of a factory line. They run a battery of diagnostic checks; if even one test fails, they kick the item off the belt and ring the alarm.

#### ──► Why It's There (Junior Context)

In a professional system architecture, data validation must happen in layers. While the constructor (`__init__`) checks basic string lengths during initial creation, the `.validate()` method acts as a dedicated gatekeeper. You call this method right before saving data to a database to guarantee that no corrupt or malformed entries slip through.

#### ──► How It Works

* The method calls the internal static helper: `self._is_valid_email(self.email)`.
* If the check returns `False`, it stops further processing and raises an `InvalidEmailException` along with an explanatory error message.
* If the validation passes cleanly, it returns `True`, giving the rest of the application the green light to proceed.

### Security Matrix Method: `def has_permission(self, required_role: str)`

#### ──► Nutshell / TL;DR

A Role-Based Access Control (RBAC) engine that evaluates whether a user's security rank meets or exceeds the required tier score.

#### ──► Company-Level Project Analogy

A military base gate ranking protocol. A 4-Star General (Rank 4) can easily walk into a basic briefing room (Rank 1 required) because their numeric rank exceeds the door's entry requirements. They don't need a separate keycard for every single room on the base.

#### ──► Why It's There (Junior Context)

Without a numeric hierarchy, managing multi-tier access requires long, messy conditional logic blocks like: `if role == "admin" or role == "analyst" or role == "shopper":`. If your company later adds a new role tier (e.g., `"manager"`), you would have to manually rewrite those chains across your entire codebase. Converting roles into numeric ranks turns security checks into a simple, scalable mathematical equation: `user_rank >= required_rank`.

#### ──► How It Works

* It maps role title strings to clear numeric ranks: `role_hierarchy = {"viewer":1, "shopper":2, "analyst":3, "admin":4}`.
* It looks up the current user's score using `.get(self.role, 0)`. If the role is missing or corrupt, it safely defaults to `0` (no clearance).
* It looks up the restriction score for the requested action, defaulting to an inaccessible `5` if an invalid role is requested.
* It returns the comparison result: `return user_rank >= required_rank`.

### Serialization Method: `def to_dict(self)`

#### ──► Nutshell / TL;DR

Flattens a complex Python user object into a plain data dictionary so it can be easily converted to a JSON string and sent over the internet to a browser or mobile app.

#### ──► Company-Level Project Analogy

Deconstructing a display piece of furniture down into a flat, compact cardboard shipping box with an explicit checklist manifest included so that an external postal carrier can easily transport it across the country.

#### ──► Why It's There (Junior Context)

Web browsers, databases, and frontend frameworks (like React or Vue) have no idea what a Python `User` object is. They only understand raw text data formats, primarily **JSON (JavaScript Object Notation)**. Python cannot directly convert a custom object instance into JSON. By providing a `.to_dict()` method, you create a translation layer that turns your complex object into a plain data structure, which can then be converted into a web-ready JSON string with a single command.

#### ──► How It Works

* It creates and returns a primitive dictionary map syntax container: `return { ... }`.
* It populates the dictionary keys with explicit string identifiers (`"user_id"`, `"email"`), and maps them directly to the object's internal values.
* Notice that it also includes `"full_name": self.full_name`. This allows it to serialize our virtual `@property` calculation, sending it over the network alongside our standard data fields.

# PART 5: The In-Memory Database Controller (UserRepository & Diagnostics)

This final department forms the **Data Management Layer** (commonly known as the **Repository Pattern**). In a large-scale corporate application, the domain model (`User`) contains the validation rules, but it shouldn't care *how* it gets saved to disk. The Repository acts as an abstraction barrier, decoupling our business data from the actual underlying storage mechanism.

---

### Class: `UserRepository`

#### ──► Nutshell / TL;DR

The transactional management layer responsible for saving, searching, filtering, and purging user profile records safely in memory.

#### ──► Company-Level Project Analogy

Think of this as the company's central **HR Filing Cabinet Room**. The folder layouts and rules are defined by the `User` forms, but the filing room itself controls how those folders are physically arranged, tracked, locked away, and searched for by name or number.

#### ──► Why It's There (Junior Context)

**Never mix your database code directly inside your data model.** If you write database saving commands directly inside your `User` class and the company later decides to switch from in-memory storage to a PostgreSQL or MongoDB cloud database, you would have to completely rewrite your core business entities. By keeping storage commands isolated inside `UserRepository`, you can swap out the database backend at any time without touching a single line of your `User` architecture.

#### ──► How It Works

* It acts as a wrapper around an internal, private data collection mapping. It exposes safe, controlled, standardized public methods (`add_user`, `get_user`) that external web API components can invoke without needing to touch raw data dictionaries directly.

---

### Method: `UserRepository.__init__(self)`

#### ──► Nutshell / TL;DR

Spins up the internal storage workspace by initializing a blank, private dictionary index map when the application boots up.

#### ──► Company-Level Project Analogy

Moving into a brand new corporate branch office and setting up a pristine, empty structural shelving organizer unit. No files exist yet, but the shelves are fully labeled and ready to hold folders.

#### ──► Why It's There (Junior Context)

Every instance of our repository needs its own isolated, secure memory storage space. Notice the leading underscore on `self._users`. In Python, this warns other developers: *"This storage dictionary is private. Do not manipulate or edit this dictionary directly from outside this class; always use the official repository tools."*

#### ──► How It Works

* `self._users: dict[int, User] = {}` assigns an empty dictionary to the instance.
* The type annotation `dict[int, User]` mandates that every unique key must be an integer (`user_id`), and every stored value must be a complete `User` object instance.

---

### Method: `UserRepository.add_user(self, user: User)`

#### ──► Nutshell / TL;DR

The gatekeeper pipeline that runs validation checks, scans for identity or email collisions, and commits the user instance safely into memory.

#### ──► Company-Level Project Analogy

An HR officer onboarding a new employee. Before sliding their file into the filing cabinet, the officer runs a strict validation checklist:

1. They verify the document is an official corporate file template.
2. They check if the employee's ID number is already assigned to a desk.
3. They look through existing files to make sure nobody else is using that corporate email address.
4. If everything clears, they officially slide the folder into the cabinet tray.

#### ──► Why It's There (Junior Context)

In a production platform, data duplication is an absolute nightmare. If two accounts share the same User ID or email, billing routers will charge the wrong credit card, and security modules will load the wrong profile permissions. This method establishes a strict transactional wall that completely blocks duplicate entries before they corrupt memory.

#### ──► How It Works

* **Type Guard:** `if not isinstance(user, User): raise TypeError(...)` ensures that a developer cannot accidentally pass a raw string or an unrelated product object into our user table.
* **Self-Audit Trigger:** It calls `user.validate()` to ensure the incoming user's data fields pass format checks (like our email format filter).
* **ID Collision Audit:** `if user.user_id in self._users` checks the dictionary keys instantly. If matched, it fires our custom `UserAlreadyExistsException` (HTTP Code 409).
* **Email Collision Audit:** It runs a loop over all existing folder entries: `for existing_user in self._users.values():`. If an email match occurs, it blocks registration.
* **Commit Step:** If all checks clear, it saves the object: `self._users[user.user_id] = user`.

### Method: `UserRepository.get_user(self, user_id: int)`

#### ──► Nutshell / TL;DR

Instantly extracts a single target user profile from the storage index map using their unique ID number.

#### ──► Company-Level Project Analogy

An assistant walking directly to box number `#12` on the storage shelf, grabbing that single physical file, and handing it over. If box `#12` is empty, they return with empty hands (`None`).

#### ──► Why It's There (Junior Context)

This is your standard point-lookup data query. When a user navigates to their profile page, the web framework reads their session ID number and calls this method to load their profile information instantly.

#### ──► How It Works

* It leverages Python's high-speed dictionary `.get()` routine: `return self._users.get(user_id, None)`.
* Instead of throwing a crash or key error if an ID doesn't exist, `.get()` safely handles missing keys by returning `None`.

### Method: `UserRepository.get_all_users(self)`

#### ──► Nutshell / TL;DR

Collects every active profile folder currently sitting in the repository index and aggregates them into a sequential, loopable list array.

#### ──► Company-Level Project Analogy

An administrative assistant pulling every single folder out of the cabinet shelves and packing them neatly into a single portable travel binder to bring to an executive board meeting.

#### ──► Why It's There (Junior Context)

This is essential for building administrative dashboards, generating corporate payroll lists, or executing batch background data tasks that process your entire active user base.

#### ──► How It Works

* It reads the dictionary's values via `self._users.values()`.
* Because raw dictionary values are returned as an un-indexable generator view object, it passes them through a clean list constructor: `return list(self._users.values())` to package them into a flexible array.

### Method: `UserRepository.get_users_by_role(self, role: str)`

#### ──► Nutshell / TL;DR

Filters down the entire user catalog to return an array subset containing only the accounts that match a requested system role string.

#### ──► Company-Level Project Analogy

An executive ordering: *"Go through the cabinet shelves and pull out copies of every single employee folder that has a pink 'Analyst' sticker on the cover tab."*

#### ──► Why It's There (Junior Context)

Corporate operations constantly require role-based isolation. For instance, if the engineering team deploys a specific security update targeted strictly at users with the `"admin"` role, this tool allows you to isolate those specific profiles in a single command.

#### ──► How It Works

* It executes an inline optimization pattern known as a **List Comprehension**: `return [user for user in self._users.values() if user.role == role]`.
* It loops through every single user profile value in the cabinet, performs an attribute string comparison check, and dynamically constructs a brand-new filtered list array to send back.

### Method: `UserRepository.delete_user(self, user_id: int)`

#### ──► Nutshell / TL;DR

Permanently destroys a target user record from the dictionary index map by looking up its identification number.

#### ──► Company-Level Project Analogy

An administrative worker pulling an outdated file out of the filing cabinet drawer and running it through a paper shredder to clear up desk storage space.

#### ──► Why It's There (Junior Context)

Crucial for corporate compliance rules, GDPR "Right to be Forgotten" privacy laws, or standard account termination flows when a user chooses to delete their profile.

#### ──► How It Works

* `if user_id not in self._users: return False` safely stops processing and returns `False` if the target ID number does not exist.
* If found, it uses the native Python memory disposal keyword: `del self._users[user_id]`. This explicitly cuts the dictionary connection pointer, causing Python's automated garbage collector to flush that object's space out of RAM. It then returns `True` to confirm a successful delete operation.

* It calls Python's high-speed structural counter: `return len(self._users)`. This operates as an $O(1)$ lookup because Python dictionaries constantly track their internal index capacity metrics automatically under the hood.

## 3. The Diagnostic Sandbox Suite: `if __name__ == "__main__":`

#### ──► Nutshell / TL;DR

A localized, automated test-runner sandbox block that triggers *only* if a software engineer executes this file directly as a script. It remains dormant if other app files import these modules.

#### ──► Company-Level Project Analogy

A car engine manufacturing warehouse testing bay. When engineers are working inside the testing bay directly on an isolated engine, they hook up simulation fuel lines and run diagnostic tests to check the oil pressure. However, when that exact same engine is shipped out and installed inside a customer's real production car, the diagnostic simulation wires are left unplugged.

#### ──► Why It's There (Junior Context)

As a junior engineer, **always test your modules locally before pushing code to the main branch.** This diagnostic block allows you to verify that your magic methods, custom exception structures, and validation parameters work as intended without spinning up an entire external database or test framework. Because it uses the `__name__` guard, it guarantees that when our real production servers import the `User` class, they won't waste cloud CPU cycles running these test logs.

#### ──► How It Works

* When a file is run directly in Python via terminal command line (`python auth.py`), Python automatically assigns a magic system global variable value: `__name__ = "__main__"`.
* If true, it activates the diagnostic routine. It walks through a series of structured `try/except` simulation gates:
* **Test 1** sets up regular users to prove normal configurations work safely, while printing properties like `.full_name`.
* **Test 2** acts as an intentional structural break test. It deliberately tries to create users with bad passwords and invalid roles. If our custom errors (`InvalidPasswordException`, `UnauthorizedException`) catch the failures, it logs a success message.
* **Test 3** tests our custom `__eq__` and `__hash__` operators by proving that placing duplicate user IDs into a Python `Set` properly deduplicates them down to a collection length of 1.
* **Test 4** verifies our `<` sorting operator (`__lt__`) by passing a scrambled list of IDs through `.sort()` and proving they arrange themselves into numerical sequence order.
* **Test 5** tests the `UserRepository` CRUD pipeline—checking insertions, intercepting database ID collision traps, running point-lookups, and executing purges.
